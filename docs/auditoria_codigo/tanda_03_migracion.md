### `unidad-4/migracion/setup_previo.sql`

**H-01 — setup_previo.sql:24 — `DELETE` físico contradice Regla dura 2. Severidad: media**

```sql
DELETE FROM usuario WHERE id IN (801, 802, 803);
```

El proyecto establece que nunca se usa `DELETE` y la baja es lógica con `eliminado = TRUE`. El archivo lo hace porque necesita re-ejecutarse, pero si `usuario` estuviera referenciado por otras tablas (ej. `pedido`), el `DELETE` fallaría o borraría historia. Las tablas dependientes de U4 sí se dropearon antes, por eso hoy funciona, pero el patrón queda asentado contra la regla.

*Corrección:* usar borrado lógico, o documentar en el encabezado que ese `DELETE` es solo para usuarios de prueba 801-803 en `copia_u4` y no aplica a usuarios reales.

**H-02 — setup_previo.sql:37-50 — `OVERRIDING SYSTEM VALUE` con IDs 501/30/801 no sincroniza sequences. Severidad: media**

Se insertan IDs explícitos (`lote 501-503`, `deposito 30-32`, `usuario 801-803`) sobre columnas `GENERATED ALWAYS AS IDENTITY`, pero no se hace `setval`. Por lectura estática, la sequence queda en el valor inicial (`1`) y un `INSERT` posterior sin ID puede generar `1, 2, …` y llegar a colisionar tarde o temprano. No ejecuté ni verifiqué la sequence, lo digo como sospecha.

*Cómo corregir:* `SELECT setval('lote_id_seq', (SELECT MAX(id) FROM lote));` para cada tabla, o usar `GENERATED BY DEFAULT`.

**H-03 — setup_previo.sql:47-50 — contraseñas de ejemplo `hash_resp801`. Severidad: baja**

Mismo patrón de `data.sql`: no es un hash real. Queda en `usuario.contrasena`, aunque no se expone por `v_usuario_seguro`.

*Cómo corregir:* hash real vía `pgcrypto/bcrypt` o comentario `solo seed de desarrollo`.

**H-04 — setup_previo.sql:27-35 — `codigo` y `nombre` sin `UNIQUE` ni control de vacío. Severidad: baja**

`lote.codigo VARCHAR(50) NOT NULL` admite duplicados y `''`.

*Cómo corregir:* `UNIQUE` si corresponde y `CHECK (btrim(codigo) <>'')`.

### `unidad-4/migracion/up.sql`

**H-05 — up.sql:56-59 — `NATURAL JOIN` frágil para la vista de compatibilidad. Severidad: baja**

```sql
FROM control_lote NATURAL JOIN responsable_deposito
```

Hoy comparten solo `responsable_control_id`, pero `NATURAL JOIN` une por *todas* las columnas con igual nombre. Si agregan una columna homónima, el join cambia silenciosamente.

*Cómo corregir:* `JOIN ... ON control_lote.responsable_control_id = responsable_deposito.responsable_control_id`.

**H-06 — up.sql:35-44 — FK `responsable_deposito.deposito_id` sin índice. Severidad: baja**

PostgreSQL no indexa FK automáticamente. Los joins/validaciones por `deposito_id` en la tabla nueva harán seq scan.

*Cómo corregir:* `CREATE INDEX ON responsable_deposito(deposito_id);`.

**H-07 — up.sql:17-31 — no se verifica existencia de `control_lote_almacen` antes de migrar. Severidad: baja**

Si `setup_previo.sql` no se corrió o la tabla fue dropeada, el `DO $$` falla con `relation does not exist` genérico, no con mensaje de precondición del enunciado.

*Cómo corregir:* verificar con `to_regclass('control_lote_almacen') IS NULL` antes y `RAISE EXCEPTION` claro.

### `unidad-4/migracion/down.sql`

**H-08 — down.sql:13-15 — `DROP ... IF EXISTS` en silencio enmascara estado incorrecto. Severidad: baja**

`up.sql` usa `CREATE TABLE` sin `IF NOT EXISTS` para fallar ruidosamente si ya se aplicó (comentario líneas 33-34). `down.sql` hace lo contrario: si no existe nada, igual hace `COMMIT` con éxito, ocultando que la migración no estaba aplicada.

*Cómo corregir:* decidir una política y documentarla. Si se quiere ruido, sacar `IF EXISTS`. Si se quiere idempotencia, decirlo en el encabezado. Hoy hay asimetría sin explicar.

**H-09 — down.sql:6-9 — aviso de pérdida de datos sin respaldo real. Severidad: media**

El encabezado dice "si se necesitara conservarlo, respaldar esas tablas antes de revertir", pero el archivo no respalda. Tras el `up`, todo lo escrito solo en `responsable_deposito`/`control_lote` se pierde con los `DROP`.

*Cómo corregir:* `CREATE TABLE ... AS` respaldo antes del `DROP`, o `pg_dump`, o advertir que el `down` es solo para el TP y no producción.

### `unidad-4/migracion/verificar_migracion.sql`

**H-10 — verificar_migracion.sql:8-13 — V1 solo enumera 3 objetos en `public`. Severidad: baja**

No verifica PKs/FKs de las tablas nuevas ni la existencia de `control_lote_almacen` (la precondición de todo). Si falta la tabla original, V1 igual da 3 filas y parece OK.

*Cómo corregir:* agregar `control_lote_almacen`, `lote`, `deposito` a la lista `IN (...)`, o una consulta separada de_constraints vía `pg_constraint`.

**H-11 — verificar_migracion.sql:16-23 — V2/V3 rompen si se ejecutan tras `down`. Severidad: baja**

Tras el `down`, `v_control_lote_almacen` no existe y V2/V3 dan error. El encabezado dice "solo tras up" para V2-V4, pero si alguien corre el archivo entero tras `down` obtiene un error, no 0 filas.

*Cómo corregir:* envolver con `IF to_regclass(...) IS NULL` o separar "solo leer tras up" de "siempre" de forma más visible — ya está en comentarios, pero el archivo no lo impone.

### `unidad-4/migracion/pruebas_falla.sql`

**H-12 — pruebas_falla.sql:27 — línea ejecutable viva en un archivo de guía. Severidad: alta**

```sql
INSERT INTO control_lote_almacen VALUES (502, 31, 801);
```

El archivo se presenta como "GUIA PARA PGADMIN, no se corre entera" (línea 2), pero esa sentencia está sin comentar. Si alguien lo corre completo en `psql/pgAdmin`, inyecta la fila violadora de `R -> D` en la base real sin `BEGIN/ROLLBACK`.

*Cómo corregir:* comentar la línea (con `--`) o envolverla en `BEGIN; … ROLLBACK;` y aclarar que hay que ejecutar solo la línea seleccionada, como se hace con V1.

**H-13 — pruebas_falla.sql:7-9 — prueba dependiente de pestañas de pgAdmin, no reproducible por CLI. Severidad: media**

El procedimiento "cerrar pestaña y elegir Rollback" es específico de pgAdmin. En `psql`/`Query Tool` en otro modo, la transacción abortada habría que cerrarla con `ROLLBACK` manual en la misma sesión. No es un bug de SQL, es de reproducibilidad.

*Cómo corregir:* agregar variantes `psql -c "ROLLBACK"` o indicación `BEGIN; ... ROLLBACK;` en vez de cerrar pestaña.

**H-14 — pruebas_falla.sql:23-30 — la prueba B insiere `(502,31)` que no viola PK, correcto, pero no verifica PK antes. Severidad: baja**

Por lectura: la PK es `(lote_id, deposito_id)` y `(502,31)` no existe aún (`502,30`, `503,31` sí), por eso el `INSERT` entra y luego falla la precondición `R -> D` de `up.sql`. El diseño es correcto, pero si la instancia cambiara a incluir `(502,31)`, el error sería de PK, no de precondición, y la prueba daría falso diagnóstico. No ejecuté para confirmar que no haya `(502,31)` en la instancia base.

*Cómo corregir:* `INSERT ... ON CONFLICT DO NOTHING` con `GET DIAGNOSTICS row_count` y abortar si `row_count=0`, o verificar con `SELECT` previo que el par no existe.
